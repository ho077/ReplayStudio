# 决策 002：播放器的"单一引擎 + 上下文播放列表"模型

- 状态：已接受（2026-10-19，Phase 2）
- 相关代码：`media/player.py`、`ui/player_page.py`、`ui/main_window.py`

## 背景与问题

Phase 2 要让软件同时承担三件事：无畏时刻片段回放、任意本地视频播放、未来的录屏成品预览。
三者共用同一个播放页。需要先定清楚两件事：

1. **播放引擎实例的粒度**：每个页面/每次播放各建一个 libmpv？还是全局只留一个？
2. **播放列表的范围**：做全局队列，还是"以当前视图为播放队列"？

## 可选方案

### 引擎粒度

| 方案 | 成本 | 风险 |
| --- | --- | --- |
| A. 每次播放新建 `MpvPlayer` | 实现简单，状态天然隔离 | 每次换片几十~上百 ms 初始化 + 硬解器重建；原生子窗口反复绑定会闪 |
| B. 单实例复用，只换文件 | 换片 <100ms，渲染窗口稳定 | 需要自己管状态复位（EOF 闩锁、pause、延迟值） |

### 播放列表范围

| 方案 | 体验 | 问题 |
| --- | --- | --- |
| C. 全局队列 | 可以跨页面攒队列 | 与"按筛选结果浏览"心智冲突；无畏时刻筛"霓虹町+捷风"后连播跑出筛选结果会很困惑 |
| D. 当前视图快照 | 连播范围 = 用户眼前看到的范围 | 离开页面后队列不会自动更新（可接受） |

## 决策

选 **B + D**：全局单引擎，播放列表为"打开时对当前视图的快照"。

实现要点：

```python
# main_window.py
def open_player(self, row, context=None):
    if context is None:
        src = self.stack.currentWidget()
        context = list(src.rows()) if hasattr(src, "rows") else [row]
    self._play_context = context
    self.player_page.set_context(context, row.get("video_id", ""))
    ...
```

## 代价

- 单实例意味着**必须显式复位状态**。Phase 2 就因此踩了两次：EOF 双通道重复上报、`pause=true` 被下一部继承。
  这些复位逻辑集中在 `play()` / `_emit_ended()` / `file-loaded` 三处，是可审计的。
- 播放上下文是快照：用户在播放时切筛选，连播仍走旧快照。这是刻意的——播放中列表突然变化更糟。

## 未来什么情况下应重新考虑

- 需要**画中画/多路同时预览**（如缩略图悬浮预览）：单实例不够，需要独立的轻量解码实例池。
- 需要**跨页面持久队列**（类似音乐播放器的"正在播放"）：应升级为独立 `PlayQueue` 服务，
  但保留"筛选结果一键入队"的操作路径。
- 若引入 libobs 把录屏预览也塞进同一引擎，需重新评估单实例是否会被录制管线阻塞。
